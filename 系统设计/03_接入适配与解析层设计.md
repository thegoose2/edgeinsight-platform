## 1. 接入与适配层

### 1.1 设计原则

- 接入层只处理"连接管理"和"身份认证"，不涉及任何业务逻辑
- 所有协议在适配层完成差异处理，进入解析层后统一为 `(connectId, rawPayload)` 两个参数
- 扩展点①：`ProtocolAdapter` 接口定义，当前实现 MQTT Adapter，TCP / OPC UA 按需扩展

### 1.2 ProtocolProfile（协议档案）

每种网关型号或设备接入方式对应一份 `ProtocolProfile`，由研发预置，交付工程师在注册设备时选用。

```
ProtocolProfile
  profile_type        唯一标识，如 "INTGATHER-V2"、"TCP-DEVICE-A"
  protocol            MQTT / TCP
  parser_id           指向 ParserRegistry 中注册的解析器
  topic_patterns      MQTT 专用：主题匹配规则
  msg_type_mapping    payload 中消息类型值 → 消息分类的映射
  frame_strategy      TCP 专用：分帧策略
```

**Device 与 ProtocolProfile 的关系：**

```
Device.device_type_id → DeviceType.profile_type → ProtocolProfile
```

- `profile_type` 不直接存在 `device` 表，通过 `device_type` 获取，确保同类型设备协议一致
- 运行时通过 `ResolvedContext` 缓存，消息处理热路径不查库

### 1.3 MQTT Adapter

#### 1.3.1 认证流程

智采极网关发起 MQTT CONNECT 请求，`DeviceAuthenticator` 实现 Moquette `IAuthenticator` 接口完成认证：

```
网关发起 CONNECT
  clientId = INTGATHER-SN-001
  username = ""（不使用）
  password = ""（不使用）
        ↓
DeviceAuthenticator
  → 查 device 表：WHERE connect_id = clientId AND lifecycle_status = 'ACTIVE'
  → 未找到：返回 CONNACK returnCode=5（拒绝），记录非法接入日志
  → 找到：返回 CONNACK returnCode=0（接受）
        ↓
认证通过
  → 加载 ResolvedContext（device_id、parser_id、validPointCodes 等）
  → 订阅该设备的上行 Topic
```

**认证说明：**
- 使用 clientId 作为身份标识，与 `device.connect_id` 一一对应
- 不使用 username/password，认证逻辑在应用层通过 connect_id 白名单实现
- 第三方网关同样遵循此机制，connect_id 在注册设备时录入

#### 1.3.2 Topic 规范

平台标准 Topic（智采极自研网关遵循）：

| Topic | 方向 | 用途 |
|------|------|------|
| `ei/{connectId}/telemetry` | 上行 | 遥测数据（温度/压力/电流等） |
| `ei/{connectId}/status` | 上行 | 心跳 + 设备在离线状态 |
| `ei/{connectId}/command` | 下行 | Platform → 网关控制指令 |
| `ei/{connectId}/command/reply` | 上行 | 网关 → Platform 指令执行结果 |

**第三方网关 Topic 适配：**

第三方网关的 Topic 规则在 `ProtocolProfile.topic_patterns` 中配置，`MqttMessageListener` 按 profile 中的规则匹配，不修改平台核心代码：

```json
// 示例：第三方网关 A 的 topic_patterns
{
  "telemetry": "/sys/{sn}/up",
  "alarm":     "/sys/{sn}/event/warn",
  "command":   "/{sn}/down"
}
```

消息类型区分规则在 `msg_type_mapping` 中配置：
```json
// payload 中 "type" 字段的值 → 消息分类
{ "103": "TELEMETRY", "3": "HEARTBEAT", "300": "ALARM" }
```

#### 1.3.3 QoS 策略

| 通道 | QoS | 说明 |
|------|------|------|
| 遥测数据上行 | QoS 1 | 时序数据幂等，重复写入不改变结果，代价远低于 QoS 2 |
| 控制指令下行 | QoS 1 | 应用层通过 command/reply + PENDING→SUCCESS/TIMEOUT 机制保障可靠性 |

#### 1.3.4 MqttMessageListener 路由逻辑

```
收到 MQTT 消息
  → 从连接上下文获取 connectId
  → 查 ResolvedContext 缓存（命中率接近 100%）
  → 按 ProtocolProfile.topic_patterns 匹配 topic → 确定消息分类
  → 若 ProtocolProfile.msg_type_mapping 不为空，进一步按 payload 字段区分
  → 路由到对应处理链：
      TELEMETRY / HEARTBEAT / ALARM / STATUS → ParserRouter
      COMMAND_REPLY → ControlService（更新指令状态）
```

### 1.4 TCP Adapter（扩展点①）

**目录 `adapter/tcp/` 故意留空**，这是一个显式的架构声明：TCP 解析器不应内置于平台，所有 TCP 解析器来自独立解析器库，项目落地时注册进 `ParserRegistry`。

TCP 接入时新增的组件（均位于 `adapter/tcp/`）：

| 组件 | 职责 |
|------|------|
| `TcpAdapterServer` | Netty ServerBootstrap，监听端口 |
| `TcpFrameDecoder` | 处理粘包/拆包，按帧切割字节流 |
| `TcpConnectionRegistry` | Map<Channel, DeviceContext>，维护连接身份 |
| `TcpAuthHandler` | 处理握手报文，完成设备认证，注册到 Registry |
| `TcpMessageHandler` | 认证后消息处理，转交 ParserRouter |

**TCP 认证与 MQTT 认证的关键区别：**

| | MQTT | TCP |
|------|------|------|
| 认证时机 | 连接建立时（协议层） | 第一条业务报文（应用层） |
| 身份携带方式 | clientId 字段 | 握手报文中约定的标识字段 |
| 认证失败处理 | Broker 拒绝连接 | TcpAuthHandler 主动关闭 Channel |
| 中间状态 | 无 | 已连接未认证（TcpConnectionRegistry 区分） |

`ParserRouter` 之上的所有层对协议完全透明，入参统一为 `(connectId, rawPayload)`。

## 2. 解析与转换层

### 2.1 设计原则

- 解析层的唯一职责：将原始报文转换为类型化的 `ParsedMessage`
- 解析层对业务逻辑层透明——业务层只认识 `ParsedMessage`，不感知任何协议细节
- 扩展点②：`ParserRegistry` 支持运行时注册，项目解析器按需接入

### 2.2 ParsedMessage 类型层次

解析层的输出契约，替代原五字段扁平结构（`StandardMessage`）：

```
ParsedMessage（抽象基类）
  device_id   String    设备标识，来自 connect_id
  timestamp   Instant   采集端时间戳，支持乱序
  msg_type    MsgType   枚举，决定实际子类型

  ├── TelemetryMessage
  │     point_code   String    测点编码
  │     value        Object    实际值（Double 或 String）
  │
  ├── HeartbeatMessage
  │     （公共字段已够用，无额外字段）
  │
  ├── DeviceAlarmMessage
  │     alarm_code   String    告警码
  │     alarm_desc   String    告警描述
  │
  └── StatusMessage
        online_status   OnlineStatus   ONLINE / OFFLINE
```

### 2.3 ParserRouter 路由链路

```
(connectId, rawPayload)
  → ResolvedContextCache.get(connectId)  → 获取 parser_id
  → ParserRegistry.get(parser_id)        → 获取解析器实例
  → parser.parse(connectId, rawPayload)  → 返回 ParsedMessage 子类型
  → 发布到 Spring ApplicationEvent 总线
```

整条链路无 if/else 判断协议类型，协议差异在 Adapter 层消化。

### 2.4 MessageParser SPI

```java
interface MessageParser {
    // 解析入口，返回对应的 ParsedMessage 子类型
    ParsedMessage parse(String connectId, byte[] rawPayload);

    // 解析器唯一标识，与 ProtocolProfile.parserId 对应
    String parserId();
}
```

### 2.5 解析器分类与来源

| 解析器 | 位置 | 来源 | 说明 |
|------|------|------|------|
| DefaultJsonParser | `parser/impl/mqtt/` | 平台内置 | 覆盖标准 key-value JSON，智采极默认使用 |
| 第三方 MQTT 网关解析器 | 解析器库 | 项目开发后沉淀 | 按需从库中选取，注册进 ParserRegistry |
| TCP 设备解析器 | 解析器库 | 项目落地前必须开发 | 100% 来自解析器库，无内置默认 |

**解析器库目录结构（独立代码仓库）：**

```
parser-library/
  mqtt/
    intgather-v2/         智采极 V2 标准 JSON 格式
    intgather-v3/
    brand-a-gateway/      第三方网关 A（标注：设备型号、接入项目）
  tcp/
    project-x-device-a/  TCP 直连设备（标注：设备型号、协议文档、接入项目）
    project-y-plc-s7/
```

**TCP 项目交付流程（比 MQTT 多一个前置步骤）：**

```
MQTT 项目：  注册 ProtocolProfile → 注册设备 → 配置测点 → 上线
TCP 项目：   分析设备协议文档 → 开发解析器 → 入库 → 注册 ProtocolProfile → 注册设备 → 配置测点 → 上线
```

解析器开发工期需纳入项目售前评估，协议文档清晰的设备约 0.5~1 天，私有二进制协议约 2~5 天。

### 2.6 TelemetryIngestService 写入校验

消息解析后进入写入流程，写入前必须校验测点合法性：

**TelemetryIngestService 完整写入流程：**

```
TelemetryMessage 到达
  → ResolvedContext.lifecycleStatus = INACTIVE → 丢弃，记 DEBUG 日志
  → ResolvedContext.validPointCodes.contains(point_code)
      不存在 → 丢弃，记 WARN 日志（上报了未注册的测点）
      存在   → 进入写入流程（同一事务）：
                 1. INSERT INTO telemetry_record（追加历史数据）
                 2. INSERT INTO telemetry_latest ... ON DUPLICATE KEY UPDATE
                    （仅当新消息 ts > 已存储 ts 时更新，乱序补传不覆盖）
               → 事务提交
               → 发布 TelemetryReceivedEvent
```

**两步写入在同一事务中执行**，保证 `telemetry_record` 和 `telemetry_latest` 的一致性。事务失败时两张表均回滚，不会出现历史数据有但最新值未更新的情况。

`validPointCodes` 来自 `device_type_point` 表（通过 `device.device_type_id`），在 `ResolvedContext` 加载时一次性缓存为 `Set<String>`，写入热路径不查库。
