| 文档版本 | V1.0 |

| 创建日期 | 2026年4月 |

## 1. 设计原则

**在线状态的权威来源是连接层，不是数据层。**

"没有数据上报"与"设备离线"是两件不同的事：
- 设备离线 → 一定没有数据
- 没有数据 → 不一定离线（待机、低频采集、无变化不上报等均属正常）

因此，`last_seen_at`（最后数据时间）仅用于运维排查，不参与离线判定。离线判定依据只有两类：**连接断开** + **网关主动上报**。

---

## 2. 三层判定机制

```
信号来源                    处理逻辑                      结果
──────────────────────────  ─────────────────────────     ──────────────
MQTT 连接断开               启动宽限期计时器              宽限期内重连 → 无事
onDisconnect 回调           delay = grace_period_secs     宽限期满未重连 → OFFLINE

网关主动上报离线             直接处理                      立即 → OFFLINE
StatusMessage(OFFLINE)      应用层主动通知，可信度最高

TCP 连接断开                同 MQTT，启动宽限期计时器      同上
channelInactive 回调
```

三种信号覆盖不同故障场景：
- MQTT/TCP 断开 + 宽限期：过滤网络抖动，避免短暂断连误报
- 网关主动上报：受控关机场景，感知最快最准
- （已移除）数据超时：不再作为离线依据，避免低频采集设备误报

### 2.1 宽限期配置

宽限期按协议类型分别配置，存储于 `system_config` 表：

| 配置键 | 默认值 | 说明 |
|------|------|------|
| `mqtt.grace_period_secs` | 30 | MQTT 客户端有自动重连，重连快 |
| `tcp.grace_period_secs` | 60 | TCP 设备重连行为取决于固件，保守设置 |

宽限期在 `ResolvedContext` 加载时按设备协议类型读取缓存，不需要每次查库。

## 3. 状态变更处理

### 3.1 设备上线

触发条件：任意消息到达（MQTT CONNECT 成功 + 数据开始上报）

```
OnlineStatusService.handleOnline(connectId)
  1. 取消该设备的宽限期计时任务（如有）
  2. 取消该设备已有的 offline 延迟任务（如有）
  3. 更新 device_status:
       online_status  = ONLINE
       connected_at   = now()
  4. 更新 device_connectivity_log:
       找最近一条 came_online_at IS NULL 的记录
       → came_online_at   = now()
       → offline_duration_s = (now - went_offline_at).seconds
  5. 发布 DeviceStatusChangedEvent(ONLINE)
```

### 3.2 设备离线

触发条件：宽限期满未重连 / 网关主动上报 StatusMessage(OFFLINE)

```
OnlineStatusService.handleOffline(connectId, cause)
  1. 计算 online_duration_s:
       上次 device_connectivity_log.came_online_at 到 now() 的秒数
       若无历史记录，使用 device_status.connected_at
  2. 更新 device_status:
       online_status    = OFFLINE
       disconnected_at  = now()
  3. 插入 device_connectivity_log:
       went_offline_at  = now()
       came_online_at   = NULL
       online_duration_s = 第1步计算值
       cause            = 传入参数
  4. 发布 DeviceStatusChangedEvent(OFFLINE)
```

### 3.3 INACTIVE 设备处理

`lifecycle_status = INACTIVE` 的设备：
- 数据到达：在 `TelemetryIngestService` 丢弃，不写库
- 连接状态：不更新 `device_status`，不记录 `device_connectivity_log`
- 状态推送：不发布 `DeviceStatusChangedEvent`

设备从 INACTIVE 切回 ACTIVE 后，下一次连接事件正常处理。

## 4. 服务重启恢复

服务重启后内存中的延迟任务全部丢失，启动时执行一次性补偿：

```
Spring 启动完成后（@EventListener ApplicationReadyEvent）
  → 查所有 lifecycle_status = ACTIVE 的设备及其 device_status
  → 对每台设备：
      if online_status = ONLINE:
          -- 查 device_connectivity_log 最近一条 came_online_at IS NULL 的记录，
          -- 取其 went_offline_at 前的最近上线时间；无则降级使用 device_status.connected_at
          计算 now - last_online_at（优先顺序：connectivity_log.came_online_at > device_status.connected_at）
          if 已超过 grace_period → 直接调用 handleOffline()
          if 未超过 → 调度剩余时长的延迟任务
      if online_status = OFFLINE:
          不需要处理
```

> **说明**：重启恢复仅使用连接时间字段（`came_online_at` / `connected_at`）判断在线时长，不使用 `last_seen_at`。`last_seen_at` 仅用于运维排查，不参与任何离线判定逻辑。

此操作是启动时的一次性扫描，不是持续轮询。

---

## 5. 统计查询支持

基于 `device_connectivity_log` 表的 `online_duration_s` + `offline_duration_s` 字段，所有统计指标直接聚合，无需复杂时间段计算：

| 指标 | 计算方式 |
|------|------|
| 总在线时长 | `SUM(online_duration_s)` |
| 总离线时长 | `SUM(offline_duration_s)` |
| 在线率 | `SUM(online_duration_s) / 统计周期总秒数` |
| 离线次数 | `COUNT(*)` |
| 平均离线时长 | `AVG(offline_duration_s)` |
| 最长单次离线 | `MAX(offline_duration_s)` |

**当前有未恢复记录时：**
当设备当前处于离线状态（`came_online_at IS NULL`），该条记录的离线时长用 `NOW() - went_offline_at` 动态计算，不影响其他已关闭记录的统计。

## 6. 与智采极协议的约定

建议在 Connect ↔ Platform 专属协议中约定：

```
智采极正常关机前，主动发送 StatusMessage(OFFLINE)
→ Platform 立即感知，无需等待宽限期
→ 适用于计划性停机、固件升级重启等场景
```

第三方网关如无此能力，依赖宽限期兜底，不影响平台正常运行。
