## 1. 扩展点总览

本平台遵循"产品层覆盖 80% 通用场景，扩展点支持项目层处理 20% 定制需求"的设计原则。扩展点是有限的、显式定义的，而非"什么都可配置"。

| 编号  | 扩展点   | 位置                                                        | 扩展方式                     | 当前实现                          |
| --- | ----- | --------------------------------------------------------- | ------------------------ | ----------------------------- |
| ①   | 协议适配器 | `edgeinsight-adapter-spi` / `ProtocolAdapter`             | 新建 adapter 模块实现接口        | edgeinsight-adapter-mqtt（已实现） |
| ②   | 解析器注册 | `edgeinsight-parser-spi` / `ParserRegistry`               | 实现 `MessageParser` 接口并注册 | DefaultJsonParser（内置）         |
| ③   | 数据存储  | `edgeinsight-core` / `repository/spi/TelemetryRepository` | 实现接口，替换 jpa/ 下的实现        | JPA 实现（V1.0）                  |

## 2. 扩展点详细说明

### 2.1 扩展点① — 协议适配器

**触发场景：** 需要接入 OPC UA、TCP 等非 MQTT 协议设备时。

**扩展方式：**

1. 新建 `edgeinsight-adapter-{protocol}` 模块，依赖 `edgeinsight-adapter-spi`、`edgeinsight-parser-spi`、`edgeinsight-core`
2. 在 `system_config` 中增加该协议的 `grace_period_secs` 配置
3. 在 `ProtocolProfile` 中新增对应记录，`protocol` 字段填写新协议标识
4. `edgeinsight-core` 及以上代码零改动

**TCP 扩展时的特殊要求：**

- `edgeinsight-adapter-mqtt/impl/tcp/` 目录当前故意留空，TCP 解析器不应内置于平台
- TCP 解析器 100% 来自解析器库，通过引用 `edgeinsight-parser-spi` 独立开发后注册进 `ParserRegistry`
- `TcpConnectionRegistry` 需区分"已连接未认证"和"已认证"两种状态
- TCP 握手报文中必须携带 `connect_id`，用于与 `device.connect_id` 匹配认证

### 2.2 扩展点② — 解析器注册

**触发场景：** 接入新型号网关或 TCP 设备时，需要开发专属解析器。

**扩展方式：**

1. 在解析器库（独立代码仓库）中引用 `edgeinsight-parser-spi` 开发解析器，实现 `MessageParser` 接口
2. 项目落地时将解析器引入 `edgeinsight-app`，调用 `ParserRegistry.register()` 注册
3. 在 `ProtocolProfile.parserId` 中填写该解析器的 `parserId`

**解析器开发规范：**

- 每个解析器是单层的，负责从原始消息到 `ParsedMessage` 子类的完整转换
- 解析器之间完全独立，互不依赖
- 完成项目交付后，解析器沉淀回解析器库，按网关型号和设备类型归类

**MQTT 解析器 vs TCP 解析器：**

| 类型 | 来源 | 内置默认 | 交付流程影响 |
|------|------|------|------|
| MQTT 解析器 | 解析器库 / 平台内置 | 有（DefaultJsonParser） | 标准格式零配置 |
| TCP 解析器 | 解析器库 | 无 | 必须先开发解析器，需纳入项目工期评估 |

### 2.3 扩展点③ — 数据存储

**触发场景：** 业务规模扩大，MySQL 无法满足时序数据存储的性能需求时。

**扩展方式：**

1. 在 `edgeinsight-core/repository/` 下新建时序数据库实现目录（如 `tdengine/`）
2. 实现 `TelemetryRepository` 接口的所有方法
3. 通过 Spring 配置切换 Bean 实现，`domain/` 层代码零改动

**接口定义（`edgeinsight-core` / `repository/spi/TelemetryRepository`）：**

```java
interface TelemetryRepository {
    // 单条写入
    void save(TelemetryRecord record);

    // 批量写入，减少数据库交互次数
    void saveBatch(List<TelemetryRecord> records);

    // 查询每个测点的最新值（从 telemetry_latest 表）
    Map<String, TelemetryRecord> findLatest(long deviceId);

    // 单测点历史数据分页查询（Spring Data JPA 风格）
    Page<TelemetryRecord> findHistory(long deviceId, String pointCode,
                                      Instant from, Instant to,
                                      Pageable pageable);

    // 流式导出，避免大数据量 OOM，Consumer 逐条处理
    void streamRange(long deviceId, String pointCode,
                     Instant from, Instant to,
                     Consumer<TelemetryRecord> sink);
}
```

**说明：**
- 分页参数使用 Spring Data JPA 的 `Pageable` / `Page<T>`，与团队其他产品保持一致
- 时间类型使用 `Instant`，与 JPA 的 `@Column` 时间映射配合使用
- 扩展点③替换时序数据库时，新实现同样使用此接口签名，上层调用代码零改动

**预估迁移工作量：** 一人一到两周。

## 3. 后续迭代扩展点

以下能力在当前版本已预留接入点，后续迭代直接接入，无需修改已有代码：

| 能力 | 预留机制 | 接入方式 |
|------|------|------|
| 告警引擎 | `TelemetryReceivedEvent`、`DeviceStatusChangedEvent` | 订阅事件，实现 AlarmEngine |
| WebSocket 实时推送 | `DeviceStatusChangedEvent`、`TelemetryReceivedEvent` | 订阅事件，实现 WebSocketPushService |
| 设备控制 | 下行指令通道架构已在 MQTT Topic 规范中预留 | 实现 ControlService + MqttPublisher |
| Andon 告警通知 | `AlarmTriggeredEvent` | 订阅事件，实现 AndonClient |
| JWT 鉴权 | `api/security/` 目录已预留 | 实现 JwtTokenProvider + JwtAuthFilter |
| 数据导出 | `TelemetryRepository.streamRange()` | 基于此接口实现导出适配器 |

## 4. 已确认技术约束

以下约束已经过业务讨论确认，作为系统设计的强制输入，不得在实现阶段变更。

### 4.1 私有化部署约束

- 所有组件必须支持纯内网离线部署
- 不能有任何硬依赖公有云服务（推送、CDN、云数据库等）
- 支持 Windows 操作系统原生部署

### 4.2 数据模型约束

- `TelemetryRepository` 必须作为抽象接口，V1.0 用 MySQL 实现，上层业务代码不得直接依赖 MySQL 实现类
- `device` 表不存 `profile_type` 字段，统一通过 `device_type_id → device_type.profile_type` 获取，确保同类型设备协议一致性
- `device` 表不存 `online_status`，独立维护于 `device_status` 表，避免高频状态更新影响核心业务表

### 4.3 测点模型约束（策略 A）

- `device_type_point` 是同类型设备测点定义的权威来源
- 不提供 `data_point_override` 机制（已讨论并移除）
- 测点的告警阈值配置由后续告警模块在告警规则表中定义，不在测点定义中承载

### 4.4 设备模型约束

- 当前业务场景为模型 A（1:1，一个网关监控一台设备），`connect_id` 直接标识设备
- `lifecycle_status` 枚举值为 `ACTIVE` / `INACTIVE`，不设 `RETIRED`（已讨论移除）
- 调试期不通过生命周期状态控制，改为在告警配置层控制（不配置告警规则即不告警）

### 4.5 解析层约束

- `TCP/` 目录故意留空，TCP 解析器不得内置于平台代码
- `ParsedMessage` 扁平结构（`StandardMessage`）已废弃，统一使用类型层次结构
- 解析器必须是单层的，负责从原始消息到 `ParsedMessage` 子类的完整转换

### 4.6 在离线判定约束

- 离线判定依据为连接层状态（断开事件 + 宽限期），不得使用数据超时作为离线判定依据
- `grace_period` 按协议类型分别配置（`mqtt.grace_period_secs` / `tcp.grace_period_secs`）
- 服务重启后必须执行一次性补偿扫描，恢复延迟任务

## 5. 设计决策记录

| 决策 | 选择 | 备选方案 | 选择理由 |
|------|------|------|------|
| 网关与设备关系 | 模型A（1:1） | 模型B（1:N） | 当前业务场景全为1:1，模型A更简单 |
| 测点模板策略 | 策略A（模板即契约） | 策略B（模板是起点） | 单工厂单项目场景，批量管理价值高 |
| 内部解耦方式 | Spring ApplicationEvent | 独立消息队列 | 零外部依赖，符合两进程部署约束 |
| 离线判定 | 连接层断开+宽限期 | 数据超时轮询 | 数据停止≠设备离线，低频采集设备会误报 |
| MQTT 认证 | connect_id 白名单 | username/password | 与现有网关使用习惯一致，无需改造固件 |
| profile_type 存储 | 仅存于 device_type | device 和 device_type 各存 | 避免设备与类型协议配置不一致的潜在错误 |
| 遥测数据存储模型 | Key-Value（行式）| 宽表（列式） | 设备类型测点可动态配置，宽表需 DDL 变更，与平台通用性冲突；重度分析需求走扩展点③切换时序数据库 |
| 最新值查询方案 | 独立 telemetry_latest 表 | 实时查 telemetry_record | 看板高频查询场景性能稳定，主键范围扫描 vs 多次索引查找 |
